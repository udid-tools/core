# Threat model

## Purpose and scope

`@udid-tools/core` generates Apple Profile Service configuration profiles,
optionally signs them, and parses and verifies device responses. It is a
framework-agnostic, server-only TypeScript library. This document models the
`0.1.x` beta scope; it is not a model for a complete MDM server, SCEP service,
HTTP application, secret store, or deployment platform.

The model must be reviewed whenever a trust boundary, cryptographic primitive,
input format, runtime dependency, release channel, or public security default
changes, and at least once per major release.

## Security objectives

The library aims to preserve:

- **Confidentiality:** signing identities, passphrases, challenges, and device
  data are not logged or copied into errors and warnings.
- **Integrity:** generated profiles are deterministic except for documented
  generated values, and signed output covers the intended plist bytes.
- **Authenticity:** signature validity and signer trust are represented as
  separate states; trust is never implied without caller-provided anchors.
- **Availability:** untrusted CMS, ASN.1, XML, and plist inputs are constrained
  by size, depth, collection, and certificate limits before expensive work.
- **Supply-chain integrity:** release artifacts are reproducible from a reviewed
  source revision, attested, and published through short-lived credentials.

## Assets

- PKCS#12/PFX bytes, private keys, and passphrases supplied by callers.
- Leaf and chain certificates supplied by callers or embedded in CMS input.
- Device identifiers and other Profile Service response attributes.
- Challenges used to correlate a request and response.
- Generated unsigned and signed mobileconfig bytes.
- Trust anchors and verification policy.
- Source code, dependency lockfile, CI configuration, npm scope, release tags,
  packages, provenance, and maintainer accounts.

## Trust boundaries and data flow

```text
Caller-controlled profile configuration
                |
                v
       validation and limits
                |
        plist serialization
                |
       optional CMS signing <--- caller-provided identity and chain
                |
                v
          generated bytes

Untrusted HTTP body (transport is outside this package)
                |
                v
      byte limits and CMS decode
                |
      signature verification <--- embedded signer certificate
                |
 optional trust-chain validation <--- caller-provided trust anchors
                |
       bounded plist parsing
                |
                v
 typed known fields + lossless raw fields + explicit verification state
```

Everything passed to the package is untrusted until validated. The host
application remains responsible for authentication, authorization, HTTPS,
request-body limits at the network edge, rate limiting, challenge issuance and
replay protection, secret retrieval, response storage, and HTTP behavior.

## Threat actors

- A remote client sending malformed or adversarial CMS/plist input.
- A developer accidentally passing incomplete, expired, mismatched, or
  incorrectly encoded signing material.
- A malicious dependency maintainer or compromised npm package.
- A contributor attempting to exfiltrate CI credentials or alter release
  artifacts.
- An attacker with a compromised maintainer, GitHub, or npm account.
- A consumer that misinterprets signature validity as certificate trust.

## Threats and mitigations

### Secret disclosure

**Threats:** a dependency, exception, logger, debug dump, test fixture, issue,
artifact, or source-control commit exposes signing material or device data.

**Mitigations:**

- No library logging, telemetry, environment reads, filesystem reads, or network
  requests.
- Structured errors and warnings use allow-listed metadata and redact secret
  inputs.
- Tests use clearly marked synthetic identities only.
- Issue and pull-request templates prohibit production secret material.
- GitHub secret scanning and push protection should be enabled at organization
  level.
- Release artifacts contain an allow-listed package file set verified with
  `npm pack`.

**Residual risk:** a host application can log returned values or input secrets;
JavaScript memory cannot guarantee zeroization because runtimes and dependencies
may copy buffers.

### Malformed input and denial of service

**Threats:** oversized CMS objects, ASN.1 complexity, deeply nested plist data,
large collections, excessive certificates, XML entity attacks, and repeated
verification consume CPU or memory or exploit a parser bug.

**Mitigations:**

- Enforce byte limits before parsing and bounded depth, collection, and
  certificate limits during validation.
- Allow-list and strip only Apple's inert plist DOCTYPE; reject custom DTDs,
  entities, and external-resource resolution.
- Reject malformed and unsupported encodings with stable errors.
- Avoid recursive algorithms without depth checks and avoid unbounded
  allocation based on attacker-controlled lengths.
- Maintain malformed-input, property-based, and resource-limit tests.
- Keep dependencies locked and monitored through Dependency Review, Dependabot,
  npm audit, CodeQL, and Scorecard.

**Residual risk:** the host must enforce request size, concurrency, rate, and
execution-time limits before invoking the package. Runtime OOM and termination
cannot be converted into a `Result`.

### Signature or trust confusion

**Threats:** accepting unsigned content, parsing content before verifying it,
trusting an embedded self-signed signer, using the wrong certificate from a
PFX, omitting certificates silently, or confusing `valid` with `trusted`.

**Mitigations:**

- CMS input and signature verification are required by the safe default parser.
- Unsigned parsing requires a separate low-level API or an explicit unsafe
  policy.
- Signature validity and trust-chain status are independent, typed fields.
- Trust validation requires explicit caller-provided anchors and never downloads
  certificates.
- Match the private key to the leaf certificate instead of relying on container
  ordering.
- Reject incomplete signing configuration, key/certificate mismatches, invalid
  signatures, and unsupported algorithms.
- Preserve unknown response fields without treating them as trusted semantics.

**Residual risk:** the caller chooses trust anchors, challenge policy, and
whether a verification warning blocks its business flow.

### Profile and configuration injection

**Threats:** dangerous URLs, duplicate fields, prototype-polluting keys, typed
fields overridden through extensions, or future Apple fields changing meaning.

**Mitigations:**

- Validate URLs, identifiers, UUIDs, plist types, duplicates, and dangerous
  property names.
- Use null-prototype internal dictionaries where applicable.
- Prevent extensions from overriding fields managed by typed APIs.
- Preserve unknown fields losslessly while exposing only known normalized
  fields through the typed result.
- Do not silently tighten or relax security defaults in a minor release.

### Dependency and install compromise

**Threats:** typosquatting, malicious install scripts, compromised transitive
dependencies, lockfile manipulation, or dependency confusion.

**Mitigations:**

- Commit and review `package-lock.json`; CI installs only with `npm ci`.
- `.npmrc` disables lifecycle scripts by default.
- Pin direct dependencies and minimize runtime dependencies.
- Require explicit review for any dependency or install-script exception.
- Automate dependency review, CodeQL, npm audit, Dependabot, and OpenSSF
  Scorecard checks.
- Build and test the packed artifact in a clean consumer context.

**Residual risk:** automated scanners have blind spots, registries and
maintainer accounts can be compromised, and dependency behavior can be
malicious without a known advisory.

### CI and release compromise

**Threats:** mutable Actions tags, broad workflow tokens, malicious fork code
with secrets, cache poisoning, tag spoofing, artifact substitution, registry
token theft, or rebuilding different artifacts for different registries.

**Mitigations:**

- Pin every Action to a full commit SHA and let Dependabot propose reviewed SHA
  updates.
- Default workflow permissions to read-only and grant writes per job.
- Never execute untrusted code through `pull_request_target`.
- Fork pull requests receive no release credentials.
- Protect `main`, release tags, and a manual-approval `release` environment.
- Validate that a release tag exactly equals the package version.
- Build one tarball, record its SHA-256, attest it, and pass it as an immutable
  workflow artifact to both registry publish jobs.
- Use npm trusted publishing (OIDC) and the job-scoped `GITHUB_TOKEN`; do not
  store long-lived registry tokens.
- Publish the SBOM and checksum with the GitHub Release.

**Residual risk:** compromise of GitHub-hosted infrastructure, organization
owners, required reviewers, or both registry and source-control identities is
outside the package boundary. Recovery procedures and hardware-backed 2FA are
organization responsibilities.

## Explicit non-goals

- Managing or protecting caller environment variables and secret stores.
- Providing HTTP authentication, authorization, CSRF protection, rate limiting,
  or transport security.
- Establishing Apple trust automatically or downloading Apple certificates.
- Supporting every cryptographic algorithm in the initial beta.
- Acting as an MDM server, SCEP server, certificate authority, or HSM client.
- Guaranteeing recovery from Node.js runtime crashes, process termination,
  native-library faults, or system-wide resource exhaustion.

## Security invariants for reviewers

A change must not merge if it violates any of these invariants:

1. No implicit network, filesystem, environment, logging, or background-task
   behavior in the library.
2. No secret-bearing input in errors, warnings, snapshots, fixtures, or release
   artifacts.
3. No trust claim without explicit anchors and successful validation.
4. No unsigned fallback after a caller supplied invalid signing options.
5. No unbounded parsing path for attacker-controlled input.
6. No third-party implementation types in the public API.
7. No mutable Action references or long-lived publishing credentials.
8. No second package build for an additional registry.

## Incident response

Follow [SECURITY.md](SECURITY.md) for private reporting. On a confirmed package
or repository compromise, maintainers should suspend publishing, revoke active
credentials and sessions, preserve audit evidence, identify affected source and
package versions, publish a GitHub security advisory, rotate signing and
recovery credentials, release a clean version from a verified revision, and
communicate exact checksums and consumer remediation steps.
